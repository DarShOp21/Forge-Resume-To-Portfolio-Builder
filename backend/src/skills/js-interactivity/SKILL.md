# JS Interactivity

You're implementing a specific, finite list of interactions against HTML
that already exists - this skill is about doing that defensively and
accessibly, not about which framework patterns to use (there isn't one;
this is vanilla JS against the real DOM).

## Query defensively, every time

The HTML was generated by a separate step and, occasionally, won't contain
exactly what's expected. Before attaching behavior to an element:
- Check a single element exists (`if (!el) return;`) before calling methods
  on it.
- Check a collection is non-empty (`if (!items.length) return;`) before
  looping or attaching per-item listeners.
- Never assume a selector match - a script that throws on a missing element
  breaks every interaction defined after it in the same file, not just the
  one that was missing its target.

## Delegate instead of attaching per-item

For any repeated element (a list of cards, a set of accordion triggers), a
single listener on the shared parent with `event.target.closest(...)` to
identify which item was interacted with is both more efficient and more
correct than one listener per item - it also automatically covers items
added to the DOM later, which a per-item loop attached once at load time
does not.

## Keep interactive JS accessible, not just clickable

A JS-driven toggle (mobile menu, accordion, dropdown, modal) has
accessibility obligations beyond making the click work:
- Toggle `aria-expanded` on the trigger element to match its actual state -
  this is the one place JS and HTML have to stay in sync, since the HTML
  stage sets the initial value but only the JS can update it at runtime.
- Support closing on `Escape` for anything that opens an overlay (modal,
  dropdown, mobile menu), and support opening/activating on `Enter`/`Space`
  for any custom interactive element that isn't a native `<button>`.
- Moving focus matters for modals/menus: when one opens, move focus into it
  (or its first focusable element); when it closes, return focus to the
  trigger that opened it, so keyboard users aren't left focused on a
  now-hidden element.
- Don't rely on `:hover` alone to reveal functionality - anything a mouse
  user can do by hovering needs a keyboard/tap equivalent.

## Build only what's on the interaction list

Every interaction implemented should trace back to a specific entry in the
architecture's interaction list - not a plausible-sounding addition. A
carousel, theme toggle, or form-validation script that wasn't asked for is
extra surface area for bugs, extra weight, and a behavior the design/content
stages never accounted for. An empty interaction list means a script that
does nothing (or doesn't exist) is the correct output, not a missed
opportunity.

## Side effects stay contained

- Wrap all DOM-touching setup in `DOMContentLoaded` so nothing runs before
  the elements it needs exist.
- Prefer small named functions over one large script body - each function
  should correspond to one interaction, making it obvious which code
  implements which listed behavior.
- Clean up what you create: a `setInterval`/`setTimeout` tied to an element
  that can be removed or hidden should be cleared, not left running against
  a detached node.
- Don't create global variables beyond what a genuinely shared piece of
  state needs; scope everything else inside the function that uses it.

## Don't restructure what the HTML/CSS stages already decided

JS should attach behavior to the existing DOM, not compensate for it -
inserting new wrapper elements, inline styles, or `className` overwrites to
fix a layout issue means the layout should have been fixed in the HTML/CSS
stages instead. The one legitimate exception is DOM creation an interaction
explicitly requires (a toast that's created and removed on submit, options
appended to a `<select>` from data) - creating structure the interaction
itself calls for is expected; patching structure the interaction doesn't
need is not.
